# AKS Newsletter – October 2026

Welcome to the October 2026 edition of the AKS Newsletter.

This month brings **3 General Availability announcements** and **6 new Preview announcements**, alongside new NAP capabilities and operational changes. Here are some of the highlights:

- **Anyscale on Azure** is now generally available
- **Managed StandardV2 NAT Gateway for AKS** is now generally available
- **Node Auto Provisioning (NAP)** adds capabilities including Capacity Reservation Groups, node image controls, and Trusted Launch
- **Windows node support for Node Auto Provisioning (NAP)** enters public preview
- **IPv4/IPv6 Dualstack support in Node Auto Provisioning (NAP) managed clusters** enters public preview
- **Updating node public IP prefixes** enters public preview

Let's dive in.

> **Correction (October 30, 2026):** An earlier version incorrectly described NAP and its October enhancements as new GA announcements. NAP's GA was [announced in July 2025](https://azure.microsoft.com/updates?id=498247). The October release notes describe additional capabilities and provisioning changes, now covered below under Behavioral Changes.

## ✅ General Availability Announcements

* **[Anyscale on Azure](https://azure.microsoft.com/en-us/updates/573744/?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Anyscale on Azure is now generally available, giving teams a managed platform for Ray-based distributed workloads. For platform engineers supporting AI infrastructure, the key tradeoff is reduced cluster-management overhead versus operating Ray directly.

* **[Managed StandardV2 NAT Gateway for AKS](https://azure.microsoft.com/en-us/updates/574430/?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: AKS now provisions and manages StandardV2 NAT Gateway for clusters using an AKS-managed virtual network. It becomes the default for new clusters using `managedNATGateway` in supported regions, so review egress infrastructure assumptions before creating clusters.

* **[Identity bindings](https://learn.microsoft.com/azure/aks/identity-bindings-concepts?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Identity bindings are now generally available, extending workload identity to address federated identity credential limits on user-assigned managed identities. This matters for platforms sharing Azure identities across many workload trust relationships, where credential limits otherwise constrain identity design.

## 🧪 Preview Feature Announcements

* **[Windows node support for Node Auto Provisioning (NAP) (preview)](https://learn.microsoft.com/azure/aks/node-autoprovision-aksnodeclass?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: NAP now supports Windows nodes in preview, extending automated capacity provisioning to Windows workloads. For mixed-OS clusters, validate Windows scheduling constraints and provisioning behavior before expanding adoption.

* **[IPv4/IPv6 Dualstack support in Node Auto Provisioning (NAP) managed clusters (preview)](https://learn.microsoft.com/azure/aks/node-auto-provisioning-networking?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10#dual-stack-networking-considerations-for-nap-preview)**: NAP-managed clusters now support IPv4/IPv6 dual-stack networking in preview. Teams adopting IPv6 can evaluate it alongside automated node provisioning, with address planning and workload connectivity worth testing together.

* **[Updating node public IP prefixes (preview)](https://learn.microsoft.com/azure/aks/use-node-public-ips?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Existing node pools can now have their node public IP prefixes updated in preview across public Azure regions. This adds flexibility when public IP allocations change, but firewall allowlists and dependencies on existing node addresses need careful coordination.

* **[Converting AKS Base clusters to AKS Automatic (preview)](https://learn.microsoft.com/azure/aks/automatic/aks-automatic-sku-migration?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Conversion from AKS Base to AKS Automatic is now available in preview for clusters with managed system node pools. This provides a migration path for existing clusters; evaluate Automatic’s operational constraints against your current configuration before converting.

* **[Ubuntu 26.04 (preview)](https://aka.ms/aks/upgrade-os-version?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Ubuntu 26.04 is now available in preview on AKS, using Ubuntu Minimal as the baseline image for Kubernetes 1.36 and later. Audit node-level agents and bootstrap scripts for dependencies on preinstalled packages before testing the new image.

* **[Windows Server OS SKU migration (preview)](https://aka.ms/aks/upgrade-windows-os-version?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: AKS now supports migrating from Windows Server 2022 to Windows Server 2025 in preview. Treat this as a workload compatibility change, not just OS maintenance: validate Windows container image compatibility and node-level tooling before migration.

## 🔁 Behavioral Changes

* **[New NAP capabilities](https://learn.microsoft.com/azure/aks/node-auto-provisioning?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: October's release notes add capabilities to NAP, which was already generally available: [Capacity Reservation Groups](https://learn.microsoft.com/azure/aks/use-capacity-reservation-groups?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10), the Capacity Buffers CRD for surplus nodes, `osDiskType` selection, [node image pinning and Kubernetes version selection](https://learn.microsoft.com/azure/aks/node-auto-provisioning-upgrade-image?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10), [Trusted Launch](https://learn.microsoft.com/azure/aks/node-autoprovision-aksnodeclass?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10#enable-trusted-launch-in-nap-clusters), [Azure Container Linux](https://learn.microsoft.com/azure/aks/node-autoprovision-aksnodeclass?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10#image-family-configuration), and [managed GPU nodes](https://learn.microsoft.com/azure/aks/aks-managed-gpu-nodes?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10). Review the controls relevant to your node lifecycle and workload requirements; this is an update to NAP, not a new GA announcement for the service.

* **[NAP provisioning changes](https://learn.microsoft.com/azure/aks/node-autoprovision?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: NAP adds instance-level public IP configuration and an AKS-managed `aksmanagednap` node pool, avoids VM SKUs within about six months of retirement, and changes default OS disk sizing and ephemeral disk eligibility checks. It also respects external load balancer exclusions when adding nodes. Review [VM size retirement guidance](https://learn.microsoft.com/azure/virtual-machines/sizes/lifecycle/retirements-and-capacity-restrictions?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10) and the [Azure Karpenter provider issue](https://github.com/Azure/karpenter-provider-azure/issues/2032) for supporting context before evaluating the impact on existing provisioning policies.

* **[Istio Gateway API ConfigMap customization](https://learn.microsoft.com/azure/aks/istio-gateway-api?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10#configmap-customizations)**: Gateway customization now supports Service `spec.ports` and Deployment seccomp profiles for the Istio add-on and Application Routing with Istio. This gives platform teams explicit control over exposed ports and gateway container hardening.

* **[Istio-based service mesh add-on](https://learn.microsoft.com/azure/aks/istio-about?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: The add-on now intercepts both IPv4 and IPv6 workload traffic on dual-stack clusters. Restart existing workloads after the update to apply the new proxy configuration and avoid leaving IPv6 traffic outside mesh interception.

* **[Application Routing Gateway API](https://learn.microsoft.com/azure/aks/app-routing-gateway-api?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: The controller now runs on the managed system node pool in AKS Automatic clusters, strengthening control-plane and data-plane isolation. Account for this placement when troubleshooting controller scheduling and availability.

* **[AKS Automatic](https://learn.microsoft.com/azure/aks/intro-aks-automatic?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: On Kubernetes 1.36+, protected system namespaces are excluded from customer mutating admission configurations. Customer webhooks and policies can still mutate customer workloads, but platform teams must stop relying on them to modify AKS-managed system workloads.

* **[Platform-managed keys for etcd encryption](https://learn.microsoft.com/azure/aks/kms-data-encryption?pivots=pmk&utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: New clusters on Kubernetes 1.37+ enable platform-managed keys for etcd encryption by default unless infrastructure encryption is explicitly configured. Review provisioning templates and compliance checks so they reflect the new encryption baseline.

* **[Azure Policy for Kubernetes](https://learn.microsoft.com/azure/governance/policy/concepts/policy-for-kubernetes?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Policies can now explicitly opt into evaluating DELETE operations, extending admission controls to resource removal. Existing policies do not enforce deletes automatically; review exemptions and cleanup workflows before enabling deletion restrictions.

* **[Flatcar preview retirement](https://aka.ms/aks/flatcar-preview-retirement?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Flatcar Container Linux node images have been removed, causing scaling, reimage, and redeploy operations to fail for affected pools. Migration to a supported node OS is now an operational requirement, not just lifecycle housekeeping.

* **[Cloud Provider Azure release notes](https://cloud-provider-azure.sigs.k8s.io/blog/2026/09/24/v1.37.0/?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: On Kubernetes 1.37, external `LoadBalancer` Services with invalid or non-public load balancer IP addresses now fail validation early. Check Service manifests and deployment templates rather than troubleshooting public IP lookup failures downstream.

* **[Cloud Provider Azure 1.36.6](https://cloud-provider-azure.sigs.k8s.io/blog/2026/09/14/v1.36.6/?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: The `service.beta.kubernetes.io/azure-pip-tags` annotation no longer overrides controller-managed public IP tags, including cluster, Service, and DNS-label ownership tags. Reserved keys are ignored case-insensitively and emit an `IgnoredPIPTagKeys` warning; remove those overrides from manifests.

* **[Platform support grace period](https://learn.microsoft.com/en-us/azure/aks/platform-initiated-upgrades?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10#platform-support-grace-period)**: Starting June 1, 2027, AKS will automatically upgrade clusters that remain on unsupported Kubernetes versions after their 60-day platform support grace period expires. Treat that deadline as an upgrade boundary, not an indefinite extension.

* **[Platform-initiated upgrades](https://learn.microsoft.com/azure/aks/platform-initiated-upgrades?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: AKS is introducing platform-initiated upgrades to move clusters off unsupported Kubernetes versions. Review upgrade channels, maintenance windows, and workload readiness before enforcement begins; postponing a planned upgrade will no longer prevent a platform-triggered one.

* **[Upgrade the OS version for your AKS node pools](https://aka.ms/aks/upgrade-os-version?utm_source=aksnewsletter&utm_medium=website&utm_campaign=2026-10)**: Starting with Kubernetes 1.38, the `Ubuntu` OS SKU defaults to Ubuntu 26.04. Explicitly select `Ubuntu2404` to retain Ubuntu 24.04, and validate OS-sensitive workloads before accepting the new default.

* **[Windows Server 2022 retirement](https://github.com/Azure/AKS/issues/4168)**: Windows Server 2022 is unsupported on Kubernetes 1.37 and later. Plan a move to a supported Windows node OS before crossing that Kubernetes version boundary, with application compatibility checks included in the upgrade rollout.
